# AI 音高模型：选型、接入与验证

YinTrace 原来用 YIN 算法测音高：导入时测原唱的人声，练习时实时测你唱的。现在**原唱的音高改用神经网络音高模型
[SwiftF0](https://github.com/lars76/swift-f0) 测**：导入时测一次，存在本地，每次练习直接用；模型用不了时仍用 YIN。
**你唱的音高仍用 YIN 实时测**（理由见[练习为什么仍用 YIN](#练习为什么仍用-yin)）。
这一页说明为什么换、换成了什么、怎么接进 App，以及和 YIN 对比的结果。

## 为什么测原唱要换掉 YIN

YIN 只看波形的周期性：一帧的差分函数够低就算有声，最低点就是周期。它在干净的人声上很准，
但分不出“这个周期是不是人声的”：分离出的人声里残留的伴奏、商业录音里的混响都会让它测错，
或者把一帧判成无声。App 只能在后面用电平门限、八度纠错、中值滤波补救。原唱的音高图是练习时评分的标准，
这里错了，你唱对了也会被判错。

神经网络音高模型是在带噪声、别的音乐和房间混响的录音上训练的，学会的是“这里哪个音高是主要的那个声音的”，
并且直接给出这一帧有没有人声的置信度。

## 选了哪个模型

| | SwiftF0 0.3.0 | CREPE | RMVPE |
|---|---|---|---|
| 许可 | MIT | MIT | 没有核实 |
| 大小 | 14 386 个参数，135 KB | tiny 约 49 万、full 约 2200 万个参数 | RVC 用的 `rmvpe.pt` 181 MB |
| 输入 | 16 kHz 音频，频谱前端在模型里 | 每帧 1024 个采样，帧和帧之间独立 | 梅尔频谱 |
| 手机上实时 | 可以：30 秒音频约 0.34 秒（这台 2.1 GHz 的云服务器，单线程） | tiny 每帧约 3700 万次乘加，每秒 100 帧负担重 | 太大，只适合离线 |
| ONNX | 官方发布的就是 ONNX | 官方是 Keras / TensorFlow 模型 | 社区转换（362 MB） |

SwiftF0 在作者的 [pitch-benchmark](https://github.com/lars76/pitch-benchmark)（19 个音高检测器）里音高 F1 最高，
与 RMVPE 在统计上持平；它小到可以随 App 附带（纯人声导入不用下载任何模型，也能用上它），在手机上测一首歌只要几秒，
许可和本项目兼容。作者的评测不能代替我们自己的，所以下面在和这个 App 一样的条件下重新比了一遍。

## 怎么接进 App

- **模型文件**：`assets/models/swift_f0.onnx`，由 `tools/build_pitch_model.py` 从 PyPI 上 swift-f0 0.3.0 的官方 wheel
  生成：权重和网络不动，只把 `fmin`、`fmax` 两个输入固定成 60 和 1400 Hz、把 float64 的 `pitch` 输出转成 float32
  （Apple 上的插件不支持 float64 张量），两个输出合成一个 `[2, 帧数]`，这样它和分离模型走同一套 `TensorModel` 接口，
  不需要改原生代码。脚本核对生成的模型和原模型算出逐位相同的置信度和音高（float32 舍入以内），CI 也会重新生成核对。
  启动时 App 把它从资源里拷到 Application Support（文件名带内容哈希，换版本不会误用旧文件）。
- **导入**（`analyzePitchWithModel`，`lib/src/analysis/pitch_track.dart`）：人声重采样到 16 kHz、归一化到峰值 −6 dBFS
  （模型本身不归一化音量，声音太小时会漏掉人声），按 30 秒一段、带 11 帧上文和 10 帧下文运行，和一次跑完整首的结果相同。
  模型 16 ms 一帧，逐字对齐用的是 5.8 ms 一帧，所以把人声错开 0、4、8、12 ms 各跑一遍，每个 5.8 ms 帧取前后两个模型帧之间
  插值的置信度（≥ 0.5 算有声）和音高。电平、频谱包络的变化、电平门限、八度纠错、中值滤波都和 YIN 时完全一样，
  所以逐字对齐看到的是同样格式的音高曲线，原来按真人演唱调好的参数不用重调。
  测出的音高曲线和逐字音高图存成这首歌的 `pitch.bin` 和 `reference.json`，以后每次练习直接读。
- **练习和自由练习**：仍用 YIN（`LivePitchTracker`，和以前完全一样），实时测麦克风里你的声音。
- **退路**：模型文件拷不出来、加载失败或运行出错时，导入改用 YIN 测完这首歌（歌曲信息 `modelInfo` 里记着
  `pitch: SwiftF0 0.3.0` 或 `YIN`，以及模型出错的原因）。
- **测试版**设置里有“原唱音高改用 YIN 算法测”，可以在同一台手机上导入同一首歌，对比两种音高图；正式版没有这个开关。

## 练习为什么仍用 YIN

模型要听到一帧之后的声音才测得准：等满 176 ms 才和一次测完整首的结果完全一样，等 80 ms 时 97–99% 的帧已经一样。
所以实时用它，音高线和读数会比 YIN（约 25 ms）晚约 70 ms 出现。导入时整首歌都在手里，没有这个问题。
练习时立刻看到自己的音高比多那一点准确更重要，所以你唱的仍用 YIN 测。

模型实时测其实更准：之前的提交 `7d7f251` 里练习也用过模型，在 MIR-1K 上戴耳机时整体准确率 94.4%（YIN 91.9%），
外放漏音时差得更多。以后如果想换，那一版的代码和测试都在 git 历史里。

原唱用模型测、你唱的用 YIN 测，会不会让评分有偏差？把同一段人声分别交给两者（296 段干声），
YIN 测出的音高比模型的中位数低 1.2 音分、平均高 1.0 音分，远小于评分 ±50 音分的容差，评分不会因此偏高或偏低。

## 验证

### 测的是什么

- **导入时测原唱**：App 先把原曲分离成人声和伴奏（MDX；打开“去和声”时再用 VR 去掉和声），
  **只拿分离出的人声测音高**，原曲只用来算伴奏（原曲减去人声）。导入“已经分离好的纯人声”时直接测这个文件。
  App 不会拿带伴奏的原曲测音高（`ImportPipeline.run`）。
- **练习时测你**：测的是麦克风里你的声音，仍用 YIN 实时测，没有换（见上面[练习为什么仍用 YIN](#练习为什么仍用-yin)）。
  所以下面只比较导入时测原唱。

### 数据和条件

[MIR-1K](http://mirlab.org/dataset/public/MIR-1K.zip)（Hsu & Jang 2010）：19 位业余歌手唱的中文流行歌片段，
人声和伴奏分在两个声道，人声音高逐帧人工标注（20 ms 一帧）。它不在 SwiftF0 0.3.0 的训练数据里
（训练用的是 MDB-stem-synth、NSynth、PTDB-TUG、MOCHA-TIMIT、CMU Arctic），评测是公平的。
每位歌手取至多 16 段，共 296 段、约 40 分钟，每段做成这些条件：

- **分离后的人声（实际的导入）**：人声和伴奏按相同能量混成“原曲”（MIR-1K 通常的混法），用 App 自己的
  人声分离代码和 UVR-MDX-NET-Voc_FT 分离（`tools/pitch_eval/separate.dart`），再测分离出的人声。
  分离把人声和其余部分之比（SI-SDR）从混音里的 0 dB 提到中位数 15.2 dB（一半的段落在 11.6–17.7 dB 之间）。
  MIR-1K 是 16 kHz 的，伴奏是 MIDI 合成的，这里的“原曲”比真实歌曲好分离；
- **干声**：只有人声，相当于分离得完美，也相当于练习时戴着耳机；
- **混响**：人声加上 RT60 0.9 秒的房间混响（−3 dB），相当于多数商业录音里的人声；
- **人声里直接混着伴奏 +5 dB / 0 dB（压力测试）**：人声里混进能量低 5 dB / 相等的伴奏，不经过分离。
  导入时不会有这样的输入；它模拟更坏的情况：分离得很差时残留的伴奏。

测的是 App 导入时测原唱的代码（YIN：`analyzePitch`；模型：`analyzePitchWithModel`），都是 App 自己的 Dart 代码，
模型通过测试用的 Python ONNX Runtime 运行。指标是旋律提取的常用指标：

- VR：标注有声的帧里测成有声的比例；VFA：标注无声的帧里测成有声的比例（越低越好）；
- RPA：标注有声的帧里音高误差在 50 音分以内的比例；RCA：同上，但差一个八度也算对；
- OA：所有帧里判断正确的比例（无声判无声、有声判有声并且音高对）；误差：音高对的帧的音分误差中位数。

### 导入：测原唱（296 段）

| 条件 | 测法 | VR | VFA | RPA | RCA | OA | 误差（音分） |
|---|---|---|---|---|---|---|---|
| **分离后的人声（实际的导入）** | YIN | 94.1 | 9.6 | 90.1 | 91.2 | 90.2 | 7.7 |
| | **SwiftF0** | **96.0** | **7.8** | **92.5** | 93.0 | **92.4** | 7.8 |
| 干声 | YIN | 95.4 | 5.5 | 93.4 | 93.7 | 93.8 | 7.3 |
| | **SwiftF0** | 96.7 | **3.3** | **95.0** | 95.2 | **95.5** | 7.5 |
| 混响 | YIN | 91.9 | 28.6 | 83.6 | 84.0 | 80.0 | 10.3 |
| | **SwiftF0** | 95.0 | 30.0 | **90.0** | 90.1 | **84.1** | 9.5 |
| 直接混着伴奏 +5 dB（压力测试） | YIN | 62.1 | 19.8 | 39.5 | 51.4 | 51.5 | 8.3 |
| | **SwiftF0** | 88.4 | 25.0 | **82.2** | 83.1 | **80.1** | 8.5 |
| 直接混着伴奏 0 dB（压力测试） | YIN | 35.8 | 22.2 | 13.9 | 23.9 | 32.7 | 9.8 |
| | **SwiftF0** | 77.6 | 27.5 | **67.0** | 68.5 | **68.6** | 9.1 |

- **实际的导入**（分离后的人声）：模型的整体准确率 92.4%，YIN 90.2%；音高对的帧 92.5% 对 90.1%，
  人声停顿处的误报 7.8% 对 9.6%，每一项都是模型更好。分离已经去掉了大部分伴奏，所以差距比下面的压力测试小。
- 干声上两者都很准，模型的误报（VFA）少了四成。
- 混响：混响的尾巴本身有音高，标注却算无声，所以两者的 VFA 都在三成左右；音高本身模型准得多（RPA 90.0 对 83.6）。
- 压力测试（不经过分离、直接混着伴奏）里差别最大：YIN 在等响的伴奏下只有 14% 的帧音高对，并且大多判成无声；
  模型仍有 67%。分离得越差，模型的优势越大。

### 音量

模型不归一化音量（`swift-f0` 的说明也这样写）。干声每 3 段取 1 段，把峰值调到不同电平：

| 峰值 | 平均电平 | VR | RPA | OA |
|---|---|---|---|---|
| −6 dBFS | −21 dBFS | 96.8 | 94.5 | 94.7 |
| −12 dBFS | −27 dBFS | 96.4 | 94.2 | 94.9 |
| −20 dBFS | −35 dBFS | 95.5 | 93.5 | 94.8 |
| −26 dBFS | −41 dBFS | 93.5 | 91.7 | 93.8 |
| −32 dBFS | −47 dBFS | 88.1 | 86.7 | 90.5 |
| −38 dBFS | −53 dBFS | 73.8 | 72.9 | 81.0 |

峰值低于 −26 dBFS 就开始漏掉人声，所以导入时先把人声归一化到峰值 −6 dBFS 再送进模型。

### 字头位置

逐字对齐靠音高曲线上有声段的起点找字头，导入时的音高曲线是 5.8 ms 一帧。在合成的两首歌（各两句、三种随机噪声，
共 102 个字，清辅音字前有噪声间隙）上，字的起点和真实起点的平均误差：YIN 5.7 ms；模型只跑一遍 5.6 ms，
错开跑两遍 4.5 ms，四遍 4.1 ms（中位数 3.5 ms）。所有方法 102 个字都在 30 ms 以内。App 用四遍。
`test/pitch_model_test.dart` 里还有一项：同一段合成演唱用模型的音高曲线对齐，85% 以上的字起点误差在 60 ms 以内，
和 YIN 的同一项测试要求相同。

### 速度

这台测试机（4 核 2.1 GHz 云服务器）上，单线程：模型跑 30 秒音频 336 ms（约 90 倍实时）。导入时 App 自己的
前后处理每分钟音频 0.7 秒，模型四遍单线程每分钟约 2.7 秒（导入时用 4 个线程），YIN 原来每分钟 1.7 秒。
iPhone 模拟器上的性能测试（CI）里，导入的“测量音高”一步 1.8 秒，人声分离 28.6 秒。

## 还没验证的

- **真机**：iPhone 上导入时模型的耗时。CI 的模拟器冒烟测试（`integration_test/ios_smoke_test.dart`）
  只检查模型在真实插件里能加载、结果正确。
- **真实的商业歌曲**：上面“分离后的人声”用的是 MIR-1K 的混音（16 kHz、业余演唱、MIDI 合成的伴奏、没有和声），
  真实歌曲全频带、有混响和和声，分离和测音高都更难，没有和人工标注对比过。
- **逐字对齐在真人演唱上**：以前用 GTSinger 调对齐参数、测准确率用的是 YIN 的音高曲线；换成模型后没有重新测
  （数据不在仓库里）。模型的音高曲线格式不变，合成演唱上的对齐测试照旧通过。
- 英文、日文歌没有单独测。

## 复现

```bash
# MIR-1K 解压到 data/MIR-1K（含 Wavfile/ 和 PitchLabel/）；数据只留在本地
pip install numpy onnxruntime
python tools/pitch_eval/render.py data/MIR-1K build/pitch-eval/audio
flutter pub get
# 像导入一样分离人声：混音 mix+0 → App 的 MDX 分离 → sep+0（需要官方的 UVR-MDX-NET-Voc_FT.onnx）
tools/fetch_models.sh build/uvr-models
dart --packages=.dart_tool/package_config.json tools/pitch_eval/separate.dart build/pitch-eval/audio build/uvr-models/UVR-MDX-NET-Voc_FT.onnx
dart --packages=.dart_tool/package_config.json tools/pitch_eval/run_app.dart build/pitch-eval/audio build/pitch-eval/tracks yin
dart --packages=.dart_tool/package_config.json tools/pitch_eval/run_app.dart build/pitch-eval/audio build/pitch-eval/tracks model
python tools/pitch_eval/score.py build/pitch-eval/audio build/pitch-eval/tracks
```

`render.py --every N` 只取每 N 段中的一段，跑得快一些。
