# 工作原理与界面设计

## 工作原理

```
音频文件 ──► 解码 (Core Audio / miniaudio) ──► 44.1 kHz 立体声
   │
   ├─► MDX-Net Voc_FT：STFT(7680/1024) → [1,4,3072,128] → ONNX → iSTFT，
   │   分块 + Hann 重叠相加（UVR demix 的移植）                  ──► 人声
   │
   ├─► VR 6_HP-Karaoke：多频带 STFT + 重采样拼接 → 全曲最大值归一化 → 512 帧窗口
   │   （与 UVR 整曲处理同一网格，每个窗口推理一次）→ ONNX 掩码 → aggressiveness →
   │   (1-mask)·X → 分频带 iSTFT 合成                              ──► 主唱
   │                                                            伴奏 = 原曲 − 主唱
   ├─► SwiftF0 音高模型（16 kHz，16 ms 一帧；错开 4 ms 跑 4 遍）→ 95 个音高格的打分
   │   → Viterbi 找整首最连贯的旋律 → 插到 5.8 ms 的帧上
   │   + 有声段（置信度起止两道门槛、离附近最响处的电平）──► 音高曲线
   │   （模型用不了时用 YIN，22.05 kHz、1024 点窗）
   │   同一帧上记录 RMS 电平，供句尾收束和音高门限使用
   │
   └─► 逐句对齐：从单声道人声按 LRC 截出每句，前后各多取 0.4 秒（句后是间奏时按这首歌的语速截短）
       → HuBERTFA 音素和边界分数 → 按词典读音强制解码（允许 SP；下一句的第一个字一起解码，字长有先验）
       → 把音素时间合并到歌词字词，按音高和电平确定句尾，提取每个字唱的音（去掉颤音、滑音）
                                                              ──► 逐字音高图（本地保存）

练习：全双工音频引擎（播放伴奏 + 采集麦克风，同一回调；iPhone 上是一个 RemoteIO 单元）给每个采集块打上
“当时正在播放的歌曲帧号”，减去系统延迟后 → 55 Hz 高通 → 实时 YIN（2048 点窗、10 ms 步长）
→ 跟随环境噪音的有声判定（背景电平、起音确认、嗡嗡声和敲击声、比歌手小很多的声音）
→ 与该时刻的参考音符（导入时用音高模型测好、存在本地）比较（可忽略八度）→ 每个字的覆盖率、音分偏差中位数、
稳定度、起唱时间 → 评分与问题标签。
```

关键实现细节：

- **分离结果与 UVR 一致**：`tools/reference/make_separation_fixtures.py` 直接运行 UVR 自己的
  `spec_utils.py` 和 MDX `demix` 代码，测试用相同的确定性“假模型”比对 Dart 实现，
  两种 karaoke 频带配置、两个 stem 的误差都在 2e-4 以内；VR 分段处理与整曲处理的差别在 1e-5 以内
  （测试用依赖整个窗口上下文的假模型，段长从 0.1 秒到 15 秒都验证过）。
  真实两个模型也按 App 的参数对照：14 秒合成混音上，MDX 信号/差值比 120.0 dB，
  VR 主唱 141.3 dB、被移除部分 118.2 dB，详见[验证记录](inference-memory.md)。
- **速度与内存**：MDX 单块滚动累加，模型推理当前块时同时计算下一块的 STFT 和上一块的逆变换。
  VR 不能一次放下整首歌的频谱，所以约 15 秒一段计算，但窗口放在 UVR 整曲处理的同一网格上：
  每个窗口只推理一次，段边界只多算几帧上下文，结果与整曲处理在浮点误差内相同，不需要交叉淡化。
  VR 期间释放混音，结束后重新解码并复用为伴奏缓冲。两个模型顺序加载、关闭，CPU arena 关闭
  （Apple 插件为此带有本地补丁）。桌面独立推理峰值 MDX 约 508 MB、VR 约 1072 MB（512 窗口）。
  导入开始时读取 iOS 报告的剩余内存（`os_proc_available_memory`），不够 512 窗口用时自动改用 320
  （约 835 MB，但推理次数是 4 倍），小内存的旧 iPhone 也能完成。真机峰值仍须用 release + Instruments 验收。
- **STFT / 重采样**：与 `torch.stft`、`librosa.stft`、`scipy.signal.resample_poly` 的数值一致（有测试）。
  采样率不是 44.1 kHz 的文件（比如 48 kHz 的 wav）先用带抗混叠滤波的多相重采样转换，
  高频不衰减，也不会多出原来没有的频率。
- **原唱的音高用音高模型 SwiftF0 测**（Lars Nieradzik，MIT）：1.4 万个参数的卷积网络，从频谱读出每 16 ms 一帧的
  音高和“这一帧有人声、音高可信”的置信度（≥ 0.5 算有声），只在 60–1400 Hz 里找。它是在语音和乐器上训练的，
  训练时混进了噪声、别的音乐和房间混响，所以分得清人声和背景，不像 YIN 只看波形周期性是否超过阈值。
  在 MIR-1K（19 位歌手的中文卡拉 OK 演唱，人工标注音高，不在它的训练数据里）上，按导入的实际做法
  （人声和伴奏混成原曲，用 App 的人声分离分出人声，再测分离出的人声）整体准确率 92.4%（YIN 90.2%），
  干声上 95.5%（YIN 93.8%）。详见[验证记录](pitch-model.md)。
  - 测的是分离出的人声（或用户导入的纯人声文件），不是原曲；测一次，存在本地，每次练习直接用。
  - 模型输出的帧间隔是 16 ms，比逐字对齐用的 5.8 ms 粗，所以把人声错开 0、4、8、12 ms 各跑一遍，
    每个 5.8 ms 帧取前后两个模型帧之间的置信度和音高。电平和频谱变化仍按原来的帧计算，
    门限、八度纠错和中值滤波也照旧，对齐看到的是同样格式的音高曲线。人声先归一化到峰值 −6 dBFS（模型本身不归一化音量）。
  - 模型加载或运行出错时，这首歌改用 YIN 测完（歌曲信息里记着用的是哪个）。
- **你唱的音高用 YIN 实时测**：差分函数用 FFT 互相关计算（O(N log N)），带抛物线插值。
  模型要听到一帧之后约 80 ms 的声音才测得准，实时显示会比 YIN 晚约 70 ms，所以练习和自由练习仍用 YIN。
  两者在同一段人声上测出的音高中位数只差约 1 音分，远小于评分的容差。
- **逐句对齐**使用 HuBERTFA v0.0.7 的 v5 ONNX 导出。模型输入是 44.1 kHz 单声道人声，
  内部重采样到 16 kHz，输出每 10 ms 的音素和边界分数。每首歌共用一个 CPU session。中文先按词组生成拼音，
  每个字的音素合成一个字区间。英文和日文用发布包里的词典。校正页设置的拼音优先于自动生成的读音。
- **一句的最后几个字**：模型把长音的韵母听成前一个字的韵母时（拖长的 ai 被听成前一个字的 e），
  解码会让前一个字唱完后面两个字，再把这两个字挤到下一句的第一个音节上；截出的片段里还有后面的间奏时，
  会挤到间奏里的和声上（一句的最后一个字被放到 7 秒后）。现在：
  - 片段延伸进下一句的那 0.4 秒里，下一句的第一个字也一起解码（只用来占住那个音节，不算进结果；
    下一句其实开始得更晚时可以不出现）；
  - 一句后面是长间奏时，片段只取“字数 × 这首歌每个字的中位时长 × 1.8”（至少 3 秒），不把间奏里的声音给这一句；
  - 少于 60 ms 的字、句中超过 1.1 秒的字逐帧加代价：句中的字很少唱那么长，句末的字常常拖长，所以句末不加。
  在两首商业歌曲上，这三条只改动了出错的句子（另外附带让下一句的第一个字从辅音开始），其中一处的结果
  与用户自己手动校正的位置相差不到 0.05 秒。
  - 模型几乎没听出来的字（两个字连着唱在同一个长音上，后一个只分到 20 ms）分到前一个字长音的最后一小段，
    不至于没有音高、不画也不计分。
- **句尾**以模型给出的最后一个字为起点，沿已保存的音高曲线和 RMS 电平查找有声尾部。
  持续约 80 ms 的无音高或低电平会结束延音，下一句句首有手动位置时优先用它划分句界，否则参考模型预测的字头。
  校正页只重对齐一句时用同样的句界：这一句提前，上一句末字的延音让出来；这一句推后或恢复，延音再沿音高轨迹接上。
  极长的 LRC 间隔最多送入模型 20 秒，已连上的长音仍可沿音高轨迹延长。
  音符来自导入时测得的音高曲线，可由 SwiftF0 或 YIN 提供。
- **同步**：伴奏播放和麦克风采集在同一个音频回调里完成，所以每个采集样本都能精确对应到歌曲位置，
  单句循环跳回时也不会错位。
- **耳返的延迟**：以前 iPhone 上的全双工由 miniaudio 实现：它开两个 RemoteIO 单元（一个录音、一个播放），
  录到的声音经过一个预先垫了两个周期的环形缓冲才交给播放回调，周期按 10 ms 申请、实际取整到 512 帧（11.6 ms），
  所以你的声音要过大约四个周期（约 40–46 ms）再加耳机和转接头本身的延迟才回到耳朵里，唱的时候能明显听出“慢半拍”。
  现在练习和自由练习用一个 RemoteIO 单元（`yt_device_ios.inc`）：在输出回调里用 `AudioUnitRender` 取同一个周期的麦克风，
  只经过一个输入周期和一个输出周期；录音时 I/O 缓冲申请 5 ms（iOS 取整为 256 帧，5.3–5.8 ms），
  按缓冲计算耳返从约 40–46 ms 降到约 11 ms（另加硬件本身的输入、输出延迟，真机上要实测）。
  耳返打开时音频会话用测量模式：默认模式下 iOS 对内置麦克风做的人声处理据报还要多几十毫秒（各机型不同），测量模式没有这一步，
  也没有自动增益（AGC 会在你不唱时把房间的噪音调响）。只有有线耳机能开耳返，所以测量模式外放变小声的缺点在这里不影响。
  - iPhone 上这个设备还会自己检查：硬件采样率变了、回调停了 1 秒、或者连续 0.5 秒取不到麦克风时，
    在控制线程上重建单元再接着放（最多 3 次，不行就暂停，让你点播放重试）。
  - 大多数 iPhone 的硬件不管 App 怎么申请都跑在 48 kHz，RemoteIO 在输入端换采样率不可靠，
    所以单元按硬件的采样率运行，回调里用 miniaudio 的线性重采样器（和以前 miniaudio 内部用的相同）
    在硬件采样率和引擎的 44.1 kHz 之间转换（`yt_rate_bridge.h`）：引擎每次正好渲染输出需要的帧数，
    同时取同样多的麦克风帧，播放和采集仍是一一对应的，转换只多约 0.2 ms。换了线路、硬件采样率变了，下一次播放时按新的采样率重建单元。
  - 来电等打断、系统停掉音频、媒体服务重启（单元要重建）都和以前一样报告给练习页；RemoteIO 建不起来时自动改用原来的 miniaudio 全双工，
    测试版“练习设置”最下面的音频事件里能看到用的是哪一种（`rio: ready …` 或 `… using miniaudio duplex`）。
  - 采集块打上的歌曲帧号和这一周期播出的是同一帧，所以自动延迟补偿（系统报告的输入、输出延迟加两个缓冲）现在正好对上；
    以前少算了环形缓冲的两个周期（约 23 ms）。

### 练习时升降调

升降调在后台逐条处理伴奏和原唱。自己实现的相位声码器把音频切成短窗，看频谱里每个音的相位怎么向前走，
再把这些短窗以新的间距合起来。一个频谱峰附近的频率共用相位修正，减少连着的音听起来发虚。
左右声道用同一套相位修正，保留原来声音在两耳之间的位置。碰到鼓点这样突然的起音，把起音固定在对应位置再接回前后的声音。

变长或变短的音频用 App 已有的多相滤波器重采样，刚好回到原来的帧数。两个步骤都从第 0 帧对齐，
所以歌词和录音仍对得上。用整段音频的均方根电平校准音量，并把峰值留在满幅以内。选原调时直接解码原音频。

练习时只在画参考线、显示目标音名和评分时加上半音数，保存的原唱音高图留在原调。“忽略八度”以换调后的音为准。
换调会把刚才唱的分数记在原先那个调里，新一遍从当前位置开始记分。已经唱了一段的录音可在换调前保存，
回听和制作成品都用录音当时的调。发给别人的歌曲从原调开始练。

处理好的音频存成 PCM WAV，切回同一个调时直接读。缓存按歌曲、音频文件内容和文件名、半音数、采样率及算法版本区分，
放在系统缓存目录，删歌时一并删除。PCM WAV 每个样本按原来的时间写入，读回时也从第 0 帧开始。

### 耳返的音量

手机麦克风录到的歌声大约 −35 到 −15 dBFS（RMS），母带处理过的伴奏在 0.9 的音量下约 −14 dBFS，
以前耳返是麦克风原样乘一个 0 到 1 的增益，所以调到最大也比伴奏低 10–20 dB，轻声的句子更听不见。
现在耳返单独走一条处理链（`packages/yintrace_audio/src/yt_monitor.h`，在音频回调里逐样本处理，不分配内存、没有前瞻延迟）：

1. 80 Hz 二阶高通：去掉低频轰鸣、喷麦和直流，免得提升之后先把余量吃掉；
2. 电平检测：5 ms 的均方（起音）加 150 ms 的释放（按 dB），读数接近一个音的 RMS，字与字之间不掉下去；
3. 压缩 / 扩展：−30 dBFS 以上 3.5:1（10 dB 软拐点），把轻重的差别收窄，轻的句子被托起；
   −55 dBFS 以下 1:3 向下扩展（最多压低 20 dB），句子之间被放大的环境噪音压下去，但不会把气声和尾音整个切掉；
4. 用户增益：0 到 16 倍（+24 dB），每个回调里平滑过渡，拖动滑块不会有“咔咔”声；
5. 峰值限制：瞬时起音、保持 15 ms、150 ms 释放，耳返里的人声峰值不超过 0.7（−3 dBFS）；
   保持时间盖过最低音的一个周期，不会把每个周期削平（+24 dB 时 82 Hz 的失真 0.4%，原来 2.7%）。

滑块按平方换算成增益：25% 等于以前的最大（0 dB），50% 为 +12 dB（一般 −24 dBFS 的歌声压缩后约 −16.5 dBFS，
和伴奏差不多响），75% 约 +19 dB，100% 为 +24 dB；增益变化用 5 ms 平滑过渡（单句循环切开的回调里也连续）。
伴奏、导唱和耳返加在一起之后，再过一个零延迟的总线限幅（瞬时起音、保持 15 ms、150 ms 释放），把整体峰值压在 0.9 以下：
人声顶着很响的伴奏时整体略微让开，而不是在每个峰上削波（超出时的失真 0.2% 以下，单靠软限幅是 8%）；
没超时增益恰好是 1，声音一点不变。最后的软限幅（|x| ≤ 0.9 完全不变，超过时平滑压向满幅）只是最后一道保险。
录音、回听和评分用的仍是原始的麦克风声音，不经过这条处理链。

耳返提升到 +24 dB 后，如果耳机里的声音漏回麦克风（一只耳塞掉出来挂在线控麦克风旁边、开放式耳机放在手机边上），
可能出现啸叫：限幅器会把它限在 −3 dBFS，但不会自己消失，这时把耳机戴好或调低耳返音量。

### 练习时的有声判定

以前每一帧单独判断：YIN 的非周期度 ≤ 0.3、电平 ≥ −50 dBFS 就算有声。iPhone 默认模式的自动增益会在你不唱时把房间调响，
电器的嗡嗡声（有清楚的周期）、敲击和打字的余响、房间里别人说话都会被画成你的音高线、算进评分。现在
（`lib/src/practice/live_pitch.dart`，YIN 本身不变）：

- YIN 前先 55 Hz 四阶高通（最低的歌唱基频约 65 Hz）；
- 跟随背景电平：用最小统计（只取不是歌声的帧，长音不会把它抬高；房间安静下来时马上降低）；
  开始一段有声要比背景高 12 dB，继续只要 6 dB（已经很周期的帧按它的非周期度少要一些），尾音不被切掉；
- 开始一段有声要有足够清楚的周期（非周期度 ≤ 0.25；比背景高 24 dB 以上时放宽到 0.3，气声、假声在安静房间里也能开始），
  最新的 1/4 帧不能比 60 ms 内最响的低 9 dB 以上（那是敲击的余响），并且连续约 30 ms；
  确认之前的帧先扣下，确认后按各自原来的时间一起交出去（不是就当作无声），所以起唱时间不变，平时也没有额外延迟；
- 电器嗡嗡声：音高（取最近 5 帧的中位数）连续 2 秒在 5 音分以内纹丝不动、又不到 −30 dBFS 的周期声音，
  在这次播放还没听到别的歌声时（或比歌声低 10 dB 以上）记为背景音；乐句之间比歌声小 10 dB 以上、
  累计 1 秒纹丝不动的声音也记为背景音。之后同一音高要比它响 12 dB 才算，背景音 10 秒没再听到就忘掉。
  人唱长音总有起伏，响亮的直音（练得很直的长音、自由练习里的乐器）不算；
- 比最近最响的乐句电平（每秒衰减 2 dB，每次播放、跳转重新开始）低 25 dB 以上的起音不算（离得远的电视、别人说话）；
  只因为这一条被挡下的声音可能是你在轻声唱，不拿来抬高背景电平；
- 在噪音里 YIN 容易选到两倍周期（低八度），有声帧会检查更短的周期是否几乎一样深，是就取更短的。

用合成的“房间里拿手机唱歌”评估（`test/support/noisy_room.dart`：带共振峰、颤音、换气和辅音的歌声，

### 逐字音高图

每个字的白色引导线来自这个字时间里的原唱音高曲线（`notesInFrames`，`lib/src/analysis/reference_notes.dart`）。
以前在音高偏离最近的中位数 0.8 个半音时切开，原唱的颤音（男声常到 ±1.5 个半音、每秒 5–6 次）每摆一次就切出一个音符，
一个长音变成上下交替的五六段，滑音也会切出一段一段的短音。现在：

1. 先用约一个颤音周期（160 ms）的滑动中位数去掉颤音：颤音只剩中心，换音仍是一步换过去，滑音仍是斜的；
2. 用 Viterbi 把它分到半音上：停在一个音不花代价，换音的代价相当于 5 帧唱偏一个半音，所以只有真正换了音并唱住才是新音符；
3. 滑音（连平滑后的音高也一直在动：起音的上滑、句尾的下落、两个音之间的滑音）不算音符，每一帧分给两边离它更近的音；
   短于 60 ms 的音并到音高更近的邻居；
4. 音符的音高取它本来唱住那部分的平均（在中位数上下 3 个半音以内），颤音给出中心，几帧的八度跳动不算；
5. 相邻、相差不到 0.8 个半音的音合成一个，中间不到 0.1 秒的断开也连上（一个长音不被切成几段）。

两首商业歌曲上（共 587 个字），一个字里音符上下来回的地方从 75 处、42 处降到 14 处、22 处，短于 80 ms 的音符
从 108 个、37 个降到 25 个、20 个，一个字最多的音符数从 6、18 降到 4；没有音符的字从 4、4 个降到 0、1 个。

练习页的纵轴：以前每一帧按视野里的音符和你最近 4 秒的音高重新算范围，滚动时一个音符进出视野、
麦克风一次测错（比如跳一个八度），纵轴都会跟着动。现在纵轴取整个半音，放得下时不动，放不下时马上放大，
比需要的大两个半音以上才收回；你的音高只算连续唱住的（至少 4 个点在一个半音以内），单个测错的点不改纵轴。
原唱的细线只画在有歌词的句子附近，前奏、间奏里的和声和哼唱不再画出来。

以前导入的歌，在歌曲页“修改歌词 → 重新对齐”时会用保存的人声重新测一遍原唱音高（`realignSong`），
再对齐、重画引导线；从别人发来的 `.yintrace` 文件导入的歌也一样。

### 模型下载

分离模型的主线路是 `hf-mirror.com`（Hugging Face 镜像上 `Blane187/all_public_uvr_models` 固定提交的同名文件，
已核对与官方文件的大小和 SHA-256 相同）。连不上、被转到 Hugging Face 主站（301/308 重定向，
在中国大陆以外会这样）、服务器报错、下载中断、半分钟内一直慢于 48 KB/秒，或者文件校验不对时，
App 自动改用备用线路：UVR 官方模型库（`github.com/TRvlvr/model_repo` 的 release），
已下载的部分接着续传。下一个分离模型先用刚才成功的线路。

HuBERTFA 的主线路是 `ghfast.top` 的 GitHub Release 镜像，备用线路是上游的官方 GitHub Release。
下载后校验 SHA-256，流式解压权重和词典，安装完成后删除压缩包。

## 界面设计

配色取自中国画的矿物颜料，每种颜色只表达一个意思：墨（文字、原唱旋律、主要按钮）、
宣纸（底色，像乐谱纸）、石绿（唱准 / 好）、朱砂（唱高了 / 差）、石青（唱低了）、
藤黄（接近 / 不稳）。练习时你的声音轨迹按音分偏差在 石青 → 石绿 → 朱砂 之间连续变色，
一眼就能看出是高了还是低了，而不只是对错。逐字音高图像乐谱一样排版：每个字的音是一笔墨线，
字写在线上方；评分页把需要加强的字做成大字卡片。支持深色模式。

`test/design_preview_test.dart` 可以用一首真实歌曲渲染所有页面的截图（浅色 / 深色），
方便检查设计：

```bash
DESIGN_SONG_DIR=<含 reference.json、pitch.bin、vocal.wav 的目录> DESIGN_LYRICS=<歌词.lrc> \
YINTRACE_AUDIO_LIB=$PWD/build/host/libyintrace_audio.so SCREENSHOT_DIR=build/design flutter test test/design_preview_test.dart
```

`test/real_vocal_test.dart` 对任意纯人声 + 歌词运行音高分析和旧版启发式对齐，供对照，并输出每个字的时间
（`REAL_VOCAL=人声.wav REAL_LYRICS=歌词.lrc REAL_OUT=输出目录`）。
